# Technical writing practice

Good documentation helps a specific audience understand a product or complete a task with minimal effort. I use the following practices as an editorial baseline and adapt them to the product, audience, and publishing system.

## Write for the audience

- Start with the user's goal, context, and level of technical knowledge.
- Keep content meaningful and concise. Add detail when it helps the user make a decision or complete a task.
- Use direct, positive language and active voice when the actor matters.
- Use meaningful link text that identifies the destination.
- Expand an abbreviation at first use, then use the abbreviation consistently.
- Use consistent product terms and user-interface labels.
- Break long sentences into shorter sentences when they contain multiple ideas.
- Add introductory text after a heading when readers need context before the next section.

## Structure task content

- Use verb-led, task-oriented headings for procedures.
- Avoid gerunds in task headings when a direct imperative works better. For example, use **Configure authentication** instead of **Configuring authentication**.
- Keep the heading hierarchy shallow. Use no more than three heading levels in most product documentation.
- Use one H1 for the page title. For long deliverables that require a separate table of contents, follow the publishing template used by that deliverable.
- Put prerequisites before procedures.
- Write procedures as numbered steps. Use bullets for unordered information.
- Keep one primary action in each numbered step where practical.
- State an expected result when users need confirmation that a step succeeded.
- Add a simple workflow or architecture diagram when sequence, components, or dependencies are easier to understand visually.
- Present parallel information in a table when a table makes comparison or scanning easier.

## Use images with purpose

- Add a screenshot when it helps users identify a control, state, or result.
- Do not repeat in prose what is already obvious in a screenshot.
- Use meaningful lowercase file names that follow the repository naming convention.
- Check image size, relevance, links, and rendered output before publication.
- Update affected screenshots when a user-interface change makes existing images inaccurate.
- Mask personal, customer, credential, and other sensitive information in screenshots.
- Avoid excessive screenshots when text, a table, or a diagram communicates the information more efficiently.

## Write links and examples safely

- Link to the relevant topic or section, not merely to a generic landing page.
- Use the destination topic name or other meaningful text for hyperlinks.
- Check internal and external links before publication.
- Use fictional names such as John Doe or Jane Doe and reserved example domains such as `example.com` in samples.
- Remove or mask application IDs, client IDs, credentials, tokens, account data, and other sensitive values from content and code samples.

## Apply Microsoft-style principles

I use Microsoft Writing Style Guide principles as an editorial baseline: user-focused instructions, concise language, active voice where appropriate, consistent terminology, accessible content, and direct procedures. Product-specific terminology and documented organizational standards take precedence when required.

The goal is consistent, usable documentation—not mechanical compliance with a rule when that rule reduces clarity.
